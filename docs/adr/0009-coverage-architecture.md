# ADR-0009: Coverage Architecture

## Status
Accepted

## Context

Code coverage for UI5 applications must be collected in the browser: the JavaScript is fetched, parsed, and evaluated at runtime by the UI5 loader, so standard Node.js coverage tools (which intercept `require`/`import`) do not apply. The test runner must inject instrumented code into the browser and extract hit-count data after each page run.

Three additional constraints shaped the design:

1. **Source files live outside the test runner's process** — they are served as static files from `configuration.webapp`. The test runner cannot simply `require()` them through an instrumented loader.
2. **nyc is not a hard dependency** — the tool must run without coverage overhead when coverage is disabled, and it must not force users to install nyc globally. The existing `Npm` class already solves on-demand installation.
3. **Coverage failures must integrate with the existing report pipeline** — threshold violations should surface as failed test results in the CTRF report, not as a separate exit-code side-channel that callers must handle differently.

## Decision

Coverage is implemented as a four-phase pipeline controlled by `configuration.coverage`:

### Phase 1 — Instrumentation (before tests)

`instrument()` in `src/modes/test/coverage/instrument.ts` runs `nyc instrument` as a subprocess. It copies source files from `configuration.webapp` into `<coverageTempDir>/instrumented/`, rewriting each file to accumulate hit counts in `window.__coverage__`.

This phase is **skipped** when `configuration.coverageSourceDir` is set. Use `coverageSourceDir` when an external server (e.g. `@ui5/cli` with `@ui5/middleware-code-coverage`) handles instrumentation on-the-fly. In that case the source files are still accessible locally for reporting purposes, but the test runner must not re-instrument them.

When `all: true` (the default), a zero-hit baseline is also generated by running `nyc` over an empty script (`node -e ""`). This ensures files that are never loaded during tests still appear in the report with 0% coverage, rather than being silently absent.

### Phase 2 — In-browser interception (`src/agent/ui5Coverage.ts`)

A small browser-side agent (`src/agent/ui5Coverage.ts`) monkey-patches `HTMLScriptElement.prototype.setAttribute` and `XMLHttpRequest.prototype.open` to append `?instrument=true` to every URL that the UI5 loader requests. The test runner's HTTP server detects this query parameter and serves the pre-instrumented copy from `<coverageTempDir>/instrumented/` instead of the original file.

The agent also proxies `window.__coverage__` from iframes to `window.top.__coverage__`, since UI5 apps typically run inside iframes and the test runner reads coverage from the top-level context.

This approach was chosen over alternatives because:
- **V8 coverage (CDP)** provides raw byte offsets, not Istanbul-compatible JSON; post-processing would need a separate toolchain and loses the `all`-files baseline. Not an option at this time.
- **Istanbul middleware** (injecting instrumentation at the HTTP layer) was not chosen because it would alter the execution context beyond the agent boundary, which is an architectural constraint.

### Phase 3 — Per-page collection (`src/modes/test/pageTask.ts`)

After each page finishes, `pageTask` reads `window.__coverage__` from the browser context and passes it to `collect()`. `collect()` writes the JSON blob to `<coverageTempDir>/<pageId>.json`. One file per page — no locking, no cross-process coordination needed because each browser agent owns its own page.

When `coverageSourceDir` is set, `collect()` rewrites every key and `path` field in the coverage blob before saving. External instrumentation tools (e.g. `@ui5/middleware-code-coverage`) use the URL pathname as the Istanbul filename, producing root-relative keys like `/controller/Main.controller.js`. nyc requires absolute filesystem paths to locate source files during reporting. `collect()` resolves these by prepending `coverageSourceDir`, turning `/controller/Main.controller.js` into `<coverageSourceDir>/controller/Main.controller.js`.

### Phase 4 — Merge and report (after all tests)

`generateReport()` in `src/modes/test/coverage/report.ts` runs two nyc subprocesses in sequence:

1. `nyc merge <coverageTempDir> <mergedPath>` — merges all per-page JSON files (including the baseline) into a single `coverage.json`.
2. `nyc report` — generates the configured reporters (default: `lcov`, `cobertura`). The `text` reporter is always appended so a summary appears in the terminal log.

Threshold checking uses `--check-coverage` with all four metric flags (`--branches`, `--functions`, `--lines`, `--statements`) passed explicitly. **All four must always be passed together** because `@istanbuljs/schema` defaults `lines` to 90 when `--check-coverage` is used — omitting any flag would silently enforce a 90% threshold for that metric.

When thresholds are not met, `generateReport()` returns a synthetic `CommonTestReport['results']` containing one failed test (`"Global code coverage check"`). This result is merged into the main CTRF report by the caller, making coverage failures visible in the same report as test failures rather than requiring callers to inspect a separate exit code.

### nyc subprocess pattern

nyc is invoked as a CLI subprocess (`node <nycBin>`) rather than called as a library because:
- nyc's programmatic API is undocumented and has changed across minor versions.
- Running it as a subprocess isolates its module graph from the test runner's, avoiding version conflicts.
- `Npm.import` + `Npm.resolvePackageDir` handle on-demand installation using the existing strategy (local → global → alternate path → install), so nyc is only present when coverage is enabled.

### Settings materialisation

Istanbul/nyc configuration is read from `configuration.coverageSettings` (default: `.nycrc.json` in the project root), merged with required overrides, and written to `<coverageTempDir>/settings/.nycrc.json`. The overrides are:

| Key | Value | Reason |
|-----|-------|--------|
| `sourceMap` | `false` | Source maps point to pre-instrumented originals, causing double-mapping |
| `coverageGlobalScope` | `"window.top"` | UI5 apps run in iframes; `window.top` is where the test runner injects |
| `coverageGlobalScopeFunc` | `false` | Prevents nyc from wrapping the scope lookup in a function, which breaks in sandboxed iframes |
| `cwd` | `configuration.coverageSourceDir ?? configuration.webapp` | Ensures relative paths in reports resolve to the source root; `coverageSourceDir` takes precedence when set |
| `exclude` | appended with temp/report/test-report dirs | Prevents coverage output from being counted as source |

Writing a materialised file (rather than passing flags directly) means all three nyc subprocess calls share a single consistent configuration without duplicating flags.

## Consequences

### Positive
- ✅ **No build-tool dependency** — instrumentation happens at the file-serving layer; no changes to the UI5 build pipeline are required
- ✅ **UI5-loader compatible** — monkey-patching `setAttribute` and `XHR.open` intercepts exactly the paths the UI5 loader uses
- ✅ **Zero overhead when disabled** — all four phases are skipped when `configuration.coverage` is false; nyc is not loaded
- ✅ **Threshold failures in CTRF** — coverage violations appear as failed tests in the standard report, requiring no caller-side special-casing
- ✅ **All-files baseline** — files never loaded during tests still appear with 0% rather than being silently absent

### Negative / Trade-offs

- ❌ **nyc subprocess overhead** — three subprocess invocations (instrument, merge, report) add wall-clock time, though the impact is negligible since each is a short-lived Node.js process and the subprocess boundary provides useful sandboxing
- ❌ **nyc version coupling** — major nyc upgrades may require changes to argument construction in `instrument.ts` and `report.ts`; mitigated by E2E test coverage which will surface CLI interface breakage
