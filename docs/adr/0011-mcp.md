# ADR-0011: MCP Mode

## Status
Accepted

## Context

The `--mcp` mode exposes `ui5-test-runner` capabilities to MCP clients (AI assistants) via an HTTP/SSE server. It covers two concerns:

1. **Knowledge base** — serving up-to-date documentation so agents can answer questions about the tool
2. **Test execution** — allowing agents to trigger, monitor, and cancel test runs, and to troubleshoot results

---

## Part 1: Knowledge Base

### Requirements

1. **Always up to date** — documentation evolves with every release; a stale KB gives wrong answers
2. **Available without credentials** — the MCP server may run in any environment; requiring a GitHub token is a deployment burden
3. **Readable as plain text** — MCP tools return markdown; HTML transformation (e.g. GitHub Pages) breaks machine consumption
4. **Discoverable** — the MCP server must be able to list topics without hardcoding paths

### Approach comparison

| Approach | Up to date | No credentials | Plain text | Discoverable |
|---|---|---|---|---|
| Embed `mcp-kb/` in npm package (build step) | ❌ only at publish time | ✅ | ✅ | ✅ |
| GitHub Pages | ❌ HTML transformed | ✅ | ❌ | ❌ |
| GitHub raw + Contents API | ✅ always `main` | ✅ public repo | ✅ | ✅ |

### Decision

The knowledge base is served from the public GitHub repository using two GitHub APIs — no credentials required.

#### File content — `raw.githubusercontent.com`

```
https://raw.githubusercontent.com/ArnaudBuchholz/ui5-test-runner/main/docs/<path>
```

Returns the file content as-is (UTF-8 markdown). No rate limiting. Used for individual file fetches.

#### Directory listing and update detection — GitHub Contents API

```
GET https://api.github.com/repos/ArnaudBuchholz/ui5-test-runner/contents/docs
```

Returns a JSON array of `{ name, path, sha, size, download_url }` entries. Unauthenticated requests are rate-limited to 60/hour — sufficient for on-demand fetches.

#### Update detection — git tree SHA

```
GET https://api.github.com/repos/ArnaudBuchholz/ui5-test-runner/git/trees/main?recursive=1
```

The top-level `sha` is the commit tree SHA. Comparing it to the locally cached SHA detects changes cheaply:

- **Same SHA** → local cache is current; no download needed
- **Different SHA** → diff per-file `sha` values; fetch only changed files via `raw.githubusercontent.com`; store the new tree SHA

#### Caching strategy

- Fetched file content is cached for the lifetime of the MCP server process
- The tree SHA, per-file SHAs, and the **timestamp of the last SHA fetch** are persisted in the temporary directory (see Part 3) to survive restarts
- On start: if the last SHA fetch is **older than 1 hour**, call `api.github.com` to get the current tree SHA; otherwise use the cached SHA
- If the SHA differs, diff per-file SHAs, fetch only changed files, update stored SHA and timestamp

## Part 1.5: Knowledge Model

### Context

Part 1 decides *how* documentation is fetched and cached. This part decides *what* the knowledge base contains and how it is structured so that an **agent we do not control** — the MCP client's LLM — can reliably answer questions ranging from installation to troubleshooting to v6 migration.

The MCP mode is **client-only**: `ui5-test-runner` ships the tools and the KB; the client brings the model, the prompt, and the retrieval loop. The design goal is therefore not to *answer* questions but to make the KB **navigable and retrievable in as few tool calls as possible, without the agent getting lost.**

### Problems with a crawl-only model

The initial model exposes `list_topics` (returns `index.md`) and `get_topic` (returns a markdown file with `[[cross-references]]`). Navigation is by *crawling* links from the index. This has three weaknesses, ranked by impact:

1. **Retrieval quality (highest impact).** To answer a question the agent must guess the topic exists, find the entry point, and walk links without exhausting its context budget. If it cannot find the door, retrieval quality is zero regardless of content quality. Crawl-only navigation is the weakest link.
2. **Growth and duplication.** Install, troubleshooting, and migration pages tend to re-explain the same option or concept. Without a single source of truth, the doc set balloons and drifts out of sync.
3. **Implicit relationships.** "This option affects that mode", "this v6 change breaks that workflow" are relationships that hand-placed `[[links]]` capture inconsistently.

### Decision

The KB is a set of **entities** — one markdown file per canonical unit of knowledge (an option, a mode, a concept, a task) — with **typed frontmatter**, from which a build step derives a **search index and a link graph**. Docs remain hand-written markdown that renders on GitHub for humans; the MCP server consumes the derived index.

This is a graph expressed **as data**, not as infrastructure: no graph database, no query language, no self-hosted embeddings. In the client-only model the client's LLM does the reasoning — **including the retrieval matching**. The server does not score or rank; it hands the LLM a compact catalog of every entity and lets the LLM pick, because vocabulary matching ("flaky test" → retries/timeouts) is exactly what the LLM is reliable at and a server-side keyword score is not. The server stays a dependency-free file/index server.

#### Entity frontmatter

Frontmatter has two layers. The **KB layer** is uniform across every entity type and is what the index and the link graph consume. The **type-specific layer** carries fields only some types need (options already have `type`, `default`, `defaultLabel`, `short`, `multiple`, `validation`, read by `build/options.mjs`; those are untouched).

This design extends the vocabulary options already use rather than inventing a new one. Options carry rich frontmatter today; modes/concepts/tasks currently carry none. The KB layer formalizes the common subset so all four types are discoverable.

**KB layer — mandatory on every entity:**

| Field | Type | Purpose |
|---|---|---|
| `id` | string | Stable identity, unique across the KB; the target of every reference and edge. **Optional — derived from the filename when absent** (see below). |
| `#type` | `option \| mode \| concept \| task` | Entity kind. Reuses the existing `#type: option` marker (`#` marks it as meta, distinct from an option's value `type`). |
| `title` | string | Agent-facing name. Options may default it from `id`. |
| `summary` | string | One-line description — the primary field the LLM matches on when browsing the catalog, and the "why" it shows the user. Options already have this. |
| `keywords` | string[] | Retrieval terms beyond the title. **Renamed from the options' existing `tags`.** |

#### Entity types (`#type`)

The four types are exhaustive and mutually exclusive — every entity is exactly one. They mirror the structure `docs/index.md` already uses (a closed set of execution modes, distinct from getting-started material).

| `#type` | Answers | Cardinality | Lives in | Examples |
|---|---|---|---|---|
| `option` | "What does this CLI flag do?" | One per CLI flag | `docs/options/` | `parallel`, `coverage`, `webapp` |
| `mode` | "What execution model am I running under?" | Closed set; a run is in exactly one | `docs/modes/` | `legacy`, `remote`, `batch` |
| `concept` | "**What is** this / how does it work?" | Open-ended, reference-style | `docs/` (top level) | `browser-selection`, `introduction`, what coverage *is* |
| `task` | "**How do I** accomplish X?" | Open-ended, goal-oriented | `docs/` (top level) | `usage`, `debug`, `mapping_v1_v2` (migration) |

**Distinguishing rules — apply in order:**

1. **Is it a CLI flag?** → `option`. (It has a value `type`, a `default`, and is read by `build/options.mjs`.)
2. **Is it one of the fixed ways the tool runs?** → `mode`. Modes are a closed, enumerable set; adding one is an architectural change. If it's not one of the runtime models, it isn't a mode.
3. **Does the page primarily explain _what something is_ or _how it works_, readable in any order?** → `concept`. Reference material; the reader is building understanding, not following steps.
4. **Does the page primarily tell the reader _how to achieve a goal_, often as an ordered sequence?** → `task`. Procedural; the reader has an objective.

**The concept vs. task boundary** is the only fuzzy one, so make it explicit:
- `concept` = *what / why* — `coverage` (what code coverage means for this tool, how instrumentation works).
- `task` = *how do I* — "set up coverage on my project" (the steps).
- They coexist and reference each other: a task links to the concepts it relies on (`see-also: [coverage]`) and to the options it sets (`requires: [options/coverage, options/coverageSourceDir]`), rather than restating them. This is the anti-duplication rule in action — **tasks are compositions of references, not new content.**

When a page seems to be both (explains a thing *and* walks through using it), split it: a `concept` for the explanation and a `task` for the procedure. That keeps each entity single-purpose and searchable.

**Relations layer — optional typed edges (this is the graph). Each value is a list of `id`s, except `breaking-in` which takes version tokens:**

| Relation | Meaning |
|---|---|
| `see-also` | Loosely related; the safe default. **Replaces the options' flat `see:` list.** |
| `affects` | This entity changes the behavior of that one (e.g. `option:coverage → mode:test`). |
| `requires` | Must be set/understood for this to work. |
| `breaking-in` | Version(s) where behavior changed/broke — the migration backbone (e.g. `[v6]`). Version tokens, not entity ids. |
| `supersedes` | Replaces a removed/renamed entity. |

**Option example** (KB layer formalized; option-specific keys untouched):

```yaml
---
"#type": option
id: coverage             # optional short handle; would otherwise derive to options/coverage
title: Code coverage
type: boolean            # option-specific, read by build/options.mjs
default: "false"         # option-specific
summary: enable code coverage
keywords: [coverage, nyc, istanbul]   # was `tags`
relations:                            # was flat `see:`
  affects: [modes/test]
  requires: [options/webapp, options/coverageSourceDir]
  see-also: [options/coverageReporters]
  breaking-in: [v6]
validation:              # option-specific
  - message: "at least one of webapp or coverageSourceDir must be set"
    conditions:
      - "!coverage || webapp !== '' || coverageSourceDir !== ''"
---
```

**Mode / concept / task example** (KB layer + relations only):

```yaml
---
"#type": mode
id: batch
title: Batch mode
summary: Execute more than one test project in a single run
keywords: [batch, parallel, multi-project]
relations:
  requires: [options/parallel]
  see-also: [modes/remote, modes/legacy]
---
```

The body is the **canonical explanation** and references other entities by id — it never restates their content.

#### KB boundary: frontmatter is the opt-in

Not every file under `docs/` is a KB entity. **A `#type` key is the opt-in**, with a two-tier rule:

- **No `#type` key → ignored.** Files with no frontmatter at all, and files whose frontmatter carries other metadata but no `#type` (e.g. the type-modifier docs' `types:` key), are not KB entities, do not enter the `id` namespace, and produce no error. Changelog, slide decks (`docs/decks/`), prompt archives (`docs/prompts/`), and raw landing pages stay as plain docs for humans.
- **`#type` present → strictly validated.** The file opts in as an entity and must carry all mandatory KB fields and pass validation, or the build fails. An invalid `#type` *value* fails loudly; only the total absence of the key is silently ignored.

This rule makes incremental migration safe: a partially-migrated `docs/` is always valid, because a page that has not yet been given frontmatter is simply not in the KB yet. The build never breaks on an un-migrated file.

#### Deriving `id` from the filename

`id` is optional. When absent, the build derives it as the **path relative to `docs/`, minus `.md`, minus a trailing `/index`** — no case transformation:

- `docs/options/coverageSourceDir.md` → `options/coverageSourceDir`
- `docs/options/types/fs-entry.md` → `options/types/fs-entry`
- `docs/modes/batch.md` → `modes/batch`
- `docs/index.md` → `index`; `docs/adr/index.md` → `adr` (trailing `/index` dropped, so these stay distinct)

**Why the full path rather than the leaf filename:** a leaf-only id means adding a new document can retroactively collide with an existing one (e.g. adding `docs/guides/coverage.md` would clash with `docs/options/coverage.md`), breaking the build on a file the author never touched — or, worse, silently pointing an edge at the wrong entity. Path-relative ids are **structurally unique**: no new file can collide with an existing one, so the failure mode is eliminated by construction rather than caught by a check.

Consequences:
- Edges are path-qualified and self-describing — `affects: [modes/test]` reveals the target's type at a glance; `requires: [options/webapp, options/coverageSourceDir]`.
- Verbatim casing is preserved, so option ids still end in their CLI flag name (`options/coverageSourceDir`).
- Two naming conventions coexist within the path (camelCase options, kebab-case type files); each id matches its file.

An explicit `id:` in frontmatter **always wins** — the escape hatch for a short stable handle on a high-traffic entity (e.g. `id: coverage`). The build still validates that every id (declared or derived) is unique and that every `relations` target resolves to a real id; a dangling edge fails the build.

#### Compatibility with the option generator

`build/options.mjs` reads only `#type`, `type`, `short`, `multiple`, `default`, `defaultLabel`, `summary`, `validation`; `build/doc.js` reads no frontmatter. Neither reads `tags` or `see`. Therefore:

- Renaming `tags` → `keywords` and replacing `see` → `relations` is a **docs-only migration** — `make options` output is unaffected.
- The additive KB fields (`id`, `title`) and `relations` are ignored by the generator.
- The **`add-option` skill template** must be updated to emit `keywords` and `relations` for new options.

#### Derived index

A `make` step aggregates all frontmatter into `kb-index.json` — one entry per entity: `id`, `#type`, `title`, `summary`, `keywords`, typed edges (`relations`), and a per-file `sha` (16 hex chars — a change-detection key, not a security digest). It is **generated on demand and gitignored**, never committed: the same `buildIndex` module runs at build time (to validate the entity model) and can run in the MCP runtime (to build the catalog from fetched docs). The index is minified on disk (it is machine-consumed; the source markdown is the human-readable form).

#### Index presentation: the LLM does the matching

The server does **not** implement keyword ranking. Instead it hands the client's LLM a **flat, filterable catalog** and lets the LLM choose the entry entities:

- **Flat, not a decision tree.** The LLM sees every entity's `id + title + summary + relations` at once and reasons globally. There is deliberately no branch the LLM must commit to before reading the leaves — a wrong first turn in a tree is unrecoverable, whereas a flat catalog has no wrong turn. This is the more reliable shape for matching, and the catalog is small enough (tens of KB, a few thousand tokens at the current scale) to return as a tool result.
- **Trimmed for context.** The catalog served to the LLM omits `keywords` and `sha`: `keywords` exist to seed the human author's synonym coverage and are consumed at *build* time (validation) — the LLM matches on `title` + `summary` + `relations`, which it reads far better than a keyword list. `sha` is a runtime cache key, of no use to the LLM.
- **Partition is a field, never a wall.** `#type` (and folder) partition the entities as *data*, so the server may return a `#type`-sliced subset on request (e.g. only the ~72 options) for context economy. But the partition is a filterable field, not a required branch: the default entry point is still the one flat catalog. This is the escape valve for when the doc set outgrows the context budget (hundreds of entities); it is an optimization, not the primary path.

`list_topics` returns this catalog. `get_topic` returns an entity's markdown plus a **"Related topics"** section derived from its `relations` edges (and their reverse) rather than relying solely on hand-placed `[[links]]` — e.g. `get_topic` on a type surfaces the modifiers whose `affects` edge points back at it. A server-side `search_kb` (keyword-ranked, returning only top hits) is **deferred**: it is only worth adding if the catalog ever grows too large to hand over whole, and the shared `buildIndex` module already produces the data it would need.

#### Two kinds of links: human-facing body links vs. the machine contract

A doc can reference another doc in two independent ways, serving two different readers. **Both are valid; do not conflate them.**

- **Relative markdown links in the body** — `[file](./modifiers/file.md)` — are **human-facing.** They exist so the docs render as clickable navigation on GitHub, resolved relative to the file's own folder. `get_topic` rewrites them best-effort so the client's LLM *can* follow them, but this is **link-text scraping, not the validated graph**: a typo or a moved file produces a silently dead reference — **the build does not check that body links resolve.** Treat them as a convenience, never as a guarantee.

- **Typed `relations` in frontmatter** — `affects: [options/types/fs-entry]` — are the **machine contract.** Values are path-qualified ids (relative to `docs/`, no `.md`, no `../`), they are **build-validated (a dangling edge fails the build)**, and they are what `get_topic` turns into the trustworthy "Related topics" section. This is the only path an author may rely on for the LLM to reliably investigate a relationship.

**Rule for authors:** use relative body links wherever a human reader benefits from clicking through — but **any relationship you want the LLM to reliably follow must also be expressed as a `relations` edge.** A body link alone is not enough for the machine. When in doubt, express an important relationship in both places; the frontmatter edge is the one that is guaranteed and surfaced.

### Anti-duplication guidelines

To keep the doc set from ballooning and enforce single source of truth:

1. **One entity, one file, one canonical explanation.** An option is explained in exactly one place.
2. **References by id, not by prose.** A page that needs concept A writes `see [[concept-a]]`; it never pastes A's explanation.
3. **Frontmatter is mandatory and typed.** No entity without `id`, `type`, `title`, `keywords`.
4. **Task pages are compositions, not content.** "Migrate to v6", "set up coverage" are sequences of references plus task-specific glue; the substance lives in entities.
5. **The build fails the doc set if** an entity is missing frontmatter, a relation points at a nonexistent id, or a body exceeds a size budget (a signal it should be split).

### Trade-offs

- ✅ Retrieval quality no longer depends on the agent guessing entry points — it reads the whole catalog and matches with its own judgement.
- ✅ Single source of truth bounds doc growth and prevents drift.
- ✅ Relationships are explicit and machine-derivable, yet stay dependency-free.
- ✅ Humans keep authoring plain markdown; GitHub keeps rendering it.
- ❌ Authoring discipline required: frontmatter and reference-by-id are enforced by the build, not optional.
- ❌ A build step (`make`) now derives `kb-index.json`; the derived index must be regenerated when docs change.

## Part 2: Test Execution Tools

### Context

Running `ui5-test-runner` is a long-running operation (seconds to minutes). The current `run` tool blocks until the process exits, which prevents the agent from observing progress or reacting to partial results.

### MCP transport and streaming

MCP's HTTP/SSE transport keeps the connection open so the server can push messages asynchronously. However, a `tools/call` still returns a single `CallToolResult` — the SSE channel carries progress notifications, but mainstream MCP clients (including Claude) do not feed those into the agent's reasoning context. Streaming partial results would require client-side changes outside the current spec.

### Decision: async polling with three tools

Rather than blocking or streaming, execution is modelled as an async job:

#### `run` — start an execution

- Spawns `ui5-test-runner` as a child process with IPC enabled (same mechanism as batch mode — see ADR-0006)
- Returns an `executionId` (timestamp-based) and the report folder path immediately
- **Errors if an execution is already in progress** — only one active execution is allowed at a time, reflecting the tool's single-run design
- The child process sends `{ type: 'progress', count, total }` IPC messages; the server stores the last received message as the current status snapshot

#### `getStatus` — poll for progress or result

- Takes the `executionId`
- Returns a **snapshot** of current state — not a delta — so the agent always has the full picture in its context without needing to remember previous calls:
  - While running: `{ status: 'running', count, total }`
  - When done: `{ status: 'done', exitCode, count, total, reportDir }`
- The `executionId` guards against stale calls (e.g. a new run started after the previous one finished)

#### `cancel` — stop the current execution

- Takes the `executionId`
- Kills the child process
- Returns immediately; the `getStatus` snapshot transitions to `done` with a non-zero exit code

### Why snapshot over delta

Agents lack reliable working memory across tool calls. A snapshot means the agent can reason from the latest `getStatus` response alone, without accumulating state across calls. Payload size is not a concern given the small shape of the status object.

### Why one execution at a time

While `ui5-test-runner` could technically support concurrent runs, the MCP execution model deliberately allows only one active execution at a time. The primary goal of the MCP mode is to let an AI agent drive and troubleshoot test runs — a use case that has no need for concurrency. When parallel execution across multiple projects is required, the `--batch` mode already handles it within a single `run` call (see ADR-0006). Returning an error when a run is already in progress is a clear signal that the agent must cancel or wait before starting a new one, keeping the interaction model simple.

## Part 3: Temporary Directory Layout

Both the KB cache and execution reports are ephemeral — they do not need to survive a machine reboot. A stable subdirectory under `os.tmpdir()` is used:

```
<os.tmpdir>/ui5-test-runner-mcp/
  kb/                        ← KB cache: tree SHA, per-file SHAs, fetched markdown
  reports/
    <executionId>/           ← one subfolder per execution (executionId = timestamp)
      report.json
      traces-*.logz
```

### Rationale

- **OS manages lifetime** — `tmpdir` is wiped on reboot on most systems (Linux/macOS/CI), which is the natural cleanup boundary for ephemeral data
- **No cleanup code** — no startup pruning, no TTL logic, no risk of deleting a report the user is still reading
- **KB survives restarts** — the SHA and timestamp persist within a session and across restarts within the same boot, satisfying the 1-hour check interval from Part 1
- **Reports are self-describing** — the `executionId` returned by `run` is the subfolder name; agents and the troubleshooting tools can locate the report folder without additional state

### Trade-offs

- On long-running machines that are rarely rebooted, reports accumulate indefinitely. This is acceptable for a developer/agent tool; CI agents typically have ephemeral environments.
- The `tmpdir` path is logged at MCP server startup so users and agents always know where to find artifacts.

## Consequences

### Positive
- ✅ **Always current KB**: reflects `main` at all times, not just at publish time
- ✅ **No build step**: no `build:mcp-kb` script, no committed generated files
- ✅ **Selective KB updates**: tree SHA diffing avoids re-downloading unchanged files
- ✅ **Retrievable KB**: the LLM matches against a compact flat catalog it reads whole; single-source-of-truth entities bound doc growth and drift
- ✅ **No credentials**: works in any environment against the public repo
- ✅ **Agent-friendly execution**: agent can observe progress and troubleshoot without blocking on a long-running tool call
- ✅ **Simple state**: single active execution, snapshot-based status, no complex lifecycle management

### Negative/Trade-offs
- ❌ **Network dependency**: KB requires internet access on first use and after updates; degrades to last cached state on outage
- ❌ **Rate limiting**: GitHub REST API limited to 60 unauthenticated calls/hour; mitigated by the 1-hour check interval
- ❌ **Report accumulation**: reports in `tmpdir` persist until reboot on long-running machines
- ❌ **No concurrent runs**: one execution at a time by design; agents must cancel or wait before starting a new run
