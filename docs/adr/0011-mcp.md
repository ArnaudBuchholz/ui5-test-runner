# ADR-0011: MCP Mode

## Status
Accepted

## Context

The `--mcp` mode exposes `ui5-test-runner` capabilities to MCP clients (AI assistants) via an HTTP/SSE server. It covers two concerns:

1. **Knowledge base** — serving up-to-date documentation so agents can answer questions about the tool
2. **Test execution** — allowing agents to trigger, monitor, and cancel test runs, and to troubleshoot results

---

## Part 1: Knowledge Base

### Requirements

1. **Always up to date** — documentation evolves with every release; a stale KB gives wrong answers
2. **Available without credentials** — the MCP server may run in any environment; requiring a GitHub token is a deployment burden
3. **Readable as plain text** — MCP tools return markdown; HTML transformation (e.g. GitHub Pages) breaks machine consumption
4. **Discoverable** — the MCP server must be able to list topics without hardcoding paths

### Approach comparison

| Approach | Up to date | No credentials | Plain text | Discoverable |
|---|---|---|---|---|
| Embed `mcp-kb/` in npm package (build step) | ❌ only at publish time | ✅ | ✅ | ✅ |
| GitHub Pages | ❌ HTML transformed | ✅ | ❌ | ❌ |
| GitHub raw + Contents API | ✅ always `main` | ✅ public repo | ✅ | ✅ |

### Decision

The knowledge base is served from the public GitHub repository using two GitHub APIs — no credentials required.

#### File content — `raw.githubusercontent.com`

```
https://raw.githubusercontent.com/ArnaudBuchholz/ui5-test-runner/main/docs/<path>
```

Returns the file content as-is (UTF-8 markdown). No rate limiting. Used for individual file fetches.

#### Directory listing and update detection — GitHub Contents API

```
GET https://api.github.com/repos/ArnaudBuchholz/ui5-test-runner/contents/docs
```

Returns a JSON array of `{ name, path, sha, size, download_url }` entries. Unauthenticated requests are rate-limited to 60/hour — sufficient for on-demand fetches.

#### Update detection — git tree SHA

```
GET https://api.github.com/repos/ArnaudBuchholz/ui5-test-runner/git/trees/main?recursive=1
```

The top-level `sha` is the commit tree SHA. Comparing it to the locally cached SHA detects changes cheaply:

- **Same SHA** → local cache is current; no download needed
- **Different SHA** → diff per-file `sha` values; fetch only changed files via `raw.githubusercontent.com`; store the new tree SHA

#### Caching strategy

- Fetched file content is cached for the lifetime of the MCP server process
- The tree SHA, per-file SHAs, and the **timestamp of the last SHA fetch** are persisted in the temporary directory (see Part 3) to survive restarts
- On start: if the last SHA fetch is **older than 1 hour**, call `api.github.com` to get the current tree SHA; otherwise use the cached SHA
- If the SHA differs, diff per-file SHAs, fetch only changed files, update stored SHA and timestamp

## Part 2: Test Execution Tools

### Context

Running `ui5-test-runner` is a long-running operation (seconds to minutes). The current `run` tool blocks until the process exits, which prevents the agent from observing progress or reacting to partial results.

### MCP transport and streaming

MCP's HTTP/SSE transport keeps the connection open so the server can push messages asynchronously. However, a `tools/call` still returns a single `CallToolResult` — the SSE channel carries progress notifications, but mainstream MCP clients (including Claude) do not feed those into the agent's reasoning context. Streaming partial results would require client-side changes outside the current spec.

### Decision: async polling with three tools

Rather than blocking or streaming, execution is modelled as an async job:

#### `run` — start an execution

- Spawns `ui5-test-runner` as a child process with IPC enabled (same mechanism as batch mode — see ADR-0006)
- Returns an `executionId` (timestamp-based) and the report folder path immediately
- **Errors if an execution is already in progress** — only one active execution is allowed at a time, reflecting the tool's single-run design
- The child process sends `{ type: 'progress', count, total }` IPC messages; the server stores the last received message as the current status snapshot

#### `getStatus` — poll for progress or result

- Takes the `executionId`
- Returns a **snapshot** of current state — not a delta — so the agent always has the full picture in its context without needing to remember previous calls:
  - While running: `{ status: 'running', count, total }`
  - When done: `{ status: 'done', exitCode, count, total, reportDir }`
- The `executionId` guards against stale calls (e.g. a new run started after the previous one finished)

#### `cancel` — stop the current execution

- Takes the `executionId`
- Kills the child process
- Returns immediately; the `getStatus` snapshot transitions to `done` with a non-zero exit code

### Why snapshot over delta

Agents lack reliable working memory across tool calls. A snapshot means the agent can reason from the latest `getStatus` response alone, without accumulating state across calls. Payload size is not a concern given the small shape of the status object.

### Why one execution at a time

While `ui5-test-runner` could technically support concurrent runs, the MCP execution model deliberately allows only one active execution at a time. The primary goal of the MCP mode is to let an AI agent drive and troubleshoot test runs — a use case that has no need for concurrency. When parallel execution across multiple projects is required, the `--batch` mode already handles it within a single `run` call (see ADR-0006). Returning an error when a run is already in progress is a clear signal that the agent must cancel or wait before starting a new one, keeping the interaction model simple.

## Part 3: Temporary Directory Layout

Both the KB cache and execution reports are ephemeral — they do not need to survive a machine reboot. A stable subdirectory under `os.tmpdir()` is used:

```
<os.tmpdir>/ui5-test-runner-mcp/
  kb/                        ← KB cache: tree SHA, per-file SHAs, fetched markdown
  reports/
    <executionId>/           ← one subfolder per execution (executionId = timestamp)
      report.json
      traces-*.logz
```

### Rationale

- **OS manages lifetime** — `tmpdir` is wiped on reboot on most systems (Linux/macOS/CI), which is the natural cleanup boundary for ephemeral data
- **No cleanup code** — no startup pruning, no TTL logic, no risk of deleting a report the user is still reading
- **KB survives restarts** — the SHA and timestamp persist within a session and across restarts within the same boot, satisfying the 1-hour check interval from Part 1
- **Reports are self-describing** — the `executionId` returned by `run` is the subfolder name; agents and the troubleshooting tools can locate the report folder without additional state

### Trade-offs

- On long-running machines that are rarely rebooted, reports accumulate indefinitely. This is acceptable for a developer/agent tool; CI agents typically have ephemeral environments.
- The `tmpdir` path is logged at MCP server startup so users and agents always know where to find artifacts.

## Consequences

### Positive
- ✅ **Always current KB**: reflects `main` at all times, not just at publish time
- ✅ **No build step**: no `build:mcp-kb` script, no committed generated files
- ✅ **Selective KB updates**: tree SHA diffing avoids re-downloading unchanged files
- ✅ **No credentials**: works in any environment against the public repo
- ✅ **Agent-friendly execution**: agent can observe progress and troubleshoot without blocking on a long-running tool call
- ✅ **Simple state**: single active execution, snapshot-based status, no complex lifecycle management

### Negative/Trade-offs
- ❌ **Network dependency**: KB requires internet access on first use and after updates; degrades to last cached state on outage
- ❌ **Rate limiting**: GitHub REST API limited to 60 unauthenticated calls/hour; mitigated by the 1-hour check interval
- ❌ **Report accumulation**: reports in `tmpdir` persist until reboot on long-running machines
- ❌ **No concurrent runs**: one execution at a time by design; agents must cancel or wait before starting a new run
